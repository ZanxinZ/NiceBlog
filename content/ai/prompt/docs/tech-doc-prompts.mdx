## 代码技术文档

技术文档通常分三类：

- **Architecture / Design**：设计思路
- **Implementation Guide**：代码如何工作的
- **Integration / Runbook**：接入说明

下面这份提示词覆盖这三类内容，用于为某个模块生成完整的技术文档。

```text title="module-doc.prompt"
请基于当前项目的实际代码，为该模块编写一份技术文档。

目标：
让一名没有参与过该模块开发的工程师，在阅读文档后能够：
1. 理解该模块解决什么问题
2. 理解整体设计和核心流程
3. 找到关键代码入口
4. 理解主要模块之间的调用关系
5. 知道如何接入、修改和扩展
6. 知道有哪些边界情况和注意事项
7. 出现问题时知道从哪里开始排查

要求：
- 必须以实际代码为事实来源，不要根据常见做法猜测实现
- 先阅读相关代码和调用链，再编写文档
- 不要逐行解释代码
- 不要简单罗列类、方法和属性
- 重点解释“为什么这样设计”和“各模块如何协作”
- 区分：现有实现 / 设计约束 / 推测
- 无法从代码确认的内容明确标记为“待确认”
- 关键流程使用 Mermaid 流程图或时序图
- 关键代码只引用必要片段，不大段复制源码
- 使用文件路径、类型名、方法名帮助开发者快速定位源码
- 内容保持简洁，不写空泛的背景介绍

文档结构：

# 模块名称

## 1. 概述
说明模块解决的问题、职责和边界。

## 2. 整体架构
说明主要组件以及它们之间的关系。
必要时提供 Mermaid 架构图。

## 3. 核心组件
说明关键类型：
- 职责
- 输入
- 输出
- 与其他组件的关系
- 对应源码位置

## 4. 核心流程
按照真实执行顺序解释主要流程。
使用 Mermaid flowchart / sequenceDiagram。

## 5. 数据与状态
说明关键数据结构、状态以及状态变化。

## 6. 异常与降级
说明失败场景、异常处理、重试、fallback、边界情况。

## 7. 接入与使用
说明其他模块应该如何使用该模块。

## 8. 修改与扩展
说明新增功能时通常需要修改哪些位置，以及现有设计的扩展点。

## 9. 调试与排查
按照“现象 → 可能原因 → 检查位置”的方式说明常见问题。

## 10. 关键源码索引
整理核心文件、类型、方法及其职责。

最后检查：
- 文档描述是否与实际代码一致
- Mermaid 中的调用关系是否真实存在
- 是否遗漏异步流程、错误流程和 fallback
- 是否存在未经代码验证的结论
- 是否出现大量没有实际信息量的描述
```

## 技术建设总结

Technical Implementation Summary：让后来的人知道「我们建设了什么、为什么这么做、现在是什么状态、怎么维护」。

```text title="tech-summary.prompt"
请基于当前项目的实际代码、配置和实现，为本次技术建设整理一份总结性技术文档。

这不是代码 API 文档，也不是逐文件代码说明。
文档目标是沉淀这项技术建设，让其他开发者能够快速理解：

- 为什么要建设它
- 它解决了什么问题
- 最终实现了什么
- 整体方案是什么
- 核心工作流程是什么
- 项目中哪些部分参与其中
- 有哪些关键技术决策
- 如何使用和维护
- 当前有哪些限制
- 后续可以如何演进

要求：

1. 以项目中的实际代码、配置和实现为事实来源
2. 先分析相关代码和调用链，再总结
3. 不要逐行解释代码
4. 不要简单罗列文件和类
5. 不要写成开发过程流水账
6. 重点总结最终形成的技术能力
7. 解释关键设计决策及其原因
8. 区分“当前实现”和“未来建议”
9. 无法从代码确认的信息标记为“待确认”
10. 必要时使用 Mermaid 图表达架构、数据流、调用链或状态流转
11. 只引用必要代码，避免大段复制源码
12. 内容简洁、工程化，避免空泛描述

建议文档结构：

# 技术建设名称

## 1. 背景
说明原来存在什么问题，以及为什么需要进行这项建设。

## 2. 建设目标
说明希望解决的问题和最终形成的能力。

## 3. 最终方案
从整体视角说明当前采用的技术方案。

必要时提供 Mermaid 架构图。

## 4. 核心机制
解释系统真正重要的几个机制。

重点回答：
- 数据从哪里来
- 如何流转
- 谁负责处理
- 如何产生最终结果
- 各模块如何协作

## 5. 关键技术决策
整理重要设计选择：

决策：
为什么这样设计：
解决的问题：
代价 / Trade-off：

只记录真正影响架构和维护的决策。

## 6. 项目实现
说明该能力在项目中的实际落点：

- 核心模块
- 关键文件
- 关键类型
- 配置
- 第三方依赖
- 服务端 / 客户端边界

重点用于帮助开发者定位代码，而不是解释每一行代码。

## 7. 使用方式
说明开发者日常如何使用这套能力。

包括：
- 如何接入
- 如何调用
- 如何配置
- 如何验证是否正常工作

## 8. 异常与降级
说明主要异常情况及系统行为。

## 9. 调试与排查
整理常见问题以及对应的排查入口。

## 10. 当前限制
明确当前方案没有解决的问题、技术约束和已知限制。

## 11. 后续演进
只记录有实际价值的改进方向，并与当前实现明确区分。

## 12. 关键资源索引
整理：
- 核心源码
- 配置文件
- 服务
- Dashboard
- 相关文档
- 外部依赖

最后检查：
- 是否准确描述了当前项目实际实现
- 是否存在未经验证的推测
- 是否遗漏关键异常流程
- 是否能让没有参与建设的人理解整套方案
- 是否写了大量可以直接从代码看出来、但没有总结价值的内容
```
